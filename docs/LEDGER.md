# hxgemm G1 실행 기록 (ledger)

계획(`docs/plans/2026-11-08-hxgemm-g1.md`)과 다르게 한 결정(Ruling)과 Task 진행을 적는다.

## Rulings

- **R1 (2026-11-10, Task 0~): 원격 단계를 로컬에서 실행.** 데스크탑 Claude가 WSL2 안에서 직접 작업하므로 "원격:" 단계는 `rsync`/`ssh desk`를 빼고 저장소 루트(`~/hxgemm`)에서 `<cmd>`만 실행한다. 결과 파일을 맥으로 옮기는 `rsync`는 `git push`로 대신한다. Task 0 Step 1~3 중 **데스크탑 쪽만 끝났다**(2026-11-10). systemd와 sshd는 이미 켜져 있었고, `PasswordAuthentication no`, 맥 공개키(`mac-to-desk`) 등록, Tailscale 설치·로그인은 사용자가 WSL 터미널에서 실행했다(맥 키 등록은 Claude가 하려다 자동 권한 검사에서 막혀 사용자가 실행). 확인 결과: sshd는 공개키 로그인만 허용하고(`PasswordAuthentication no`) Tailscale 망 안에서만 접속한다. **맥 쪽은 아직이다:** 맥 `~/.ssh/config`의 `Host desk` 블록이 없고, `tailscale status`에 이 데스크탑만 보여 맥이 같은 tailnet에 로그인했는지 확인되지 않았다(Task 0 Step 2의 "맥에도 Tailscale 앱 설치·로그인"). 따라서 `ssh desk` 연결은 아직 검증되지 않았다.

- **R2 (2026-11-10, Task 1): `cmake_minimum_required`를 3.24 → 3.22로 낮춤.** 데스크탑 cmake가 3.22.1(Ubuntu 22.04 apt)이다. 계획의 CMakeLists가 쓰는 기능(`CMAKE_CUDA_ARCHITECTURES`, `FindCUDAToolkit`/`CUDA::cublas`, `file(GLOB CONFIGURE_DEPENDS)`)은 3.22에 모두 있어, 새 cmake를 설치하지 않고 최소 버전만 낮췄다.
- **R3 (2026-11-10): 클럭은 Windows 관리자 권한으로 1500 MHz 고정.** WSL 안에서는 권한이 없어 `-lgc`가 실패하고, Windows 관리자 cmd의 `nvidia-smi -lgc 1500,1500`은 성공한다(스펙 환경 기록). 측정 전에 사용자가 고정하고, 클럭 로그는 그대로 같이 남긴다.

- **R4 (2026-11-10, Task 2): CUDA 컴파일러를 `/usr/local/cuda/bin/nvcc`(12.2)로 고정.** 처음 configure에서 CMake가 apt `nvidia-cuda-toolkit`의 `/usr/bin/nvcc`(11.5)와 `/usr/lib/x86_64-linux-gnu/libcublas.so.11`을 골랐다. 이렇게 빌드한 `hxgemm_bench`는 첫 CUDA 호출에서 `no CUDA-capable device is detected`로 끝났고, `LD_DEBUG=libs`로 보니 WSL용 `/usr/lib/wsl/lib/libcuda.so.1`이 아니라 apt `libnvidia-compute-580`의 `/lib/x86_64-linux-gnu/libcuda.so`(580.178.04)가 로드됐다. `CMakeLists.txt`에서 `CMAKE_CUDA_COMPILER`/`CUDACXX`가 지정되지 않았고 `/usr/local/cuda/bin/nvcc`가 있으면 그것을 쓰도록 바꾸고 `build/`를 새로 만들었다. 이후 cuBLAS는 `/usr/local/cuda/lib64/libcublas.so.12`로 링크되고 정상 동작한다. Task 1의 `check_args`/devinfo도 12.2로 다시 빌드해 같은 결과를 확인했다. 시스템 패키지(nvcc 11.5, libnvidia-compute-*)는 건드리지 않았다 → KNOWN_ISSUES 후보.

- **R7 (2026-11-10, 중간 리뷰): 큰 크기 검증 기준을 cuBLAS → GPU FP64 naive 커널로 변경.** max(M,N,K) > 512이면 `bench/hxgemm_bench.cu`의 `ref_gpu_fp64`(원소당 스레드 1개, FP64 누적, β = 0이면 C0를 읽지 않음)로 기준을 만든다. cuBLAS도 이 기준으로 검증된다. 결과 행에 출력 비트의 FNV-1a 해시(`fnv=`, stdout만, CSV 열은 그대로)를 추가했다. 결과: k01~k05 출력은 1000³/2047³/4096³에서 비트 단위로 같고, cuBLAS는 2047³에서만 같다(KNOWN_ISSUES #4, 해결로 이동). 4096³ 기준 계산은 수 초.
- **R8 (2026-11-10, Task 7 Step 1): `unsupported_tile_rejected`는 추가하자마자 통과했다.** K05 `{128,128,32,4,4,3}`은 98,304 B로 opt-in 한도 101,376 B 이하라 `HXGEMM_OK`(rc=0)가 기대값이고 실제도 0. 없는 조합 `{96,96,8,8,8,2}`, stages=4, K04에 stages=2는 −2. Task 6 구현(`run`의 한도 검사, `HX_CASE`의 stages 분기)이 이미 이 동작을 만들고 있어, 테스트는 그 동작을 고정한 것이다(계획 Step 1에 적힌 경우).

- **R13 (2회차): k05 B 열 배치를 4개 묶음 간격 배치로 변경.** 근거(ncu, 8192³, 큰 타일): shared load bank conflict 1,073,741,824회, "uncoalesced shared accesses 32 %"(Est. 31.95 %). 코드상 TN=8이면 이웃 스레드가 32 B 간격으로 읽음. 변경: 스레드의 TN 열을 TN/4개 묶음으로 나눠 묶음 q를 `q*(BN/(TN/4)) + tx*4`에 둠(TN=4는 그대로). 결과: conflict 0, 4096³ 8387 → **8777 GFLOPS(94.4 %)**, 8192³ 8839 → **9116(81.3 %)**(`2026-11-10_r2_final.csv`). 출력 비트는 이전과 같음(4096³ 해시 `45e5410fa35be654`). 4096³ k05 전체 재sweep(112 타일)에서도 128x256x16x16x8x3이 1위(`2026-11-10_r2sweep_final.csv`).

- R15 (2회차 후, 블루스크린 전): k05 기본 타일을 128x256x16x16x8x3으로 바꿨다가 작은 모양에서 크게 느려짐을 측정(`2026-11-10_tuned_final.csv`: 128×4096² 7014 → 3841, 16×4096² 893 → 485, 512³ 3158 → 1736). 커밋 전 블루스크린(측정·파일은 손실 없음). → R16으로 대체.
- **R16 (사용자 결정 "1번"): k05 기본 타일을 모양에 따라 선택.** `hxgemm_default_tile()`(공개 API 추가): 128x256 블록 수 ceil(M/128)·ceil(N/256) ≥ 256이면 128x256x16x16x8x3, 아니면 128x128x32x8x4x2. 규칙 근거: 두 타일을 22개 모양에서 같은 실행으로 비교(`2026-11-10_heur_final.csv`). 블록 수만으로는 단조롭지 않아(32·64·96블록은 큰 타일, 128·192블록은 작은 타일이 빠름) 큰 손실을 피하는 문턱 256을 골랐다. "블록 수 ≥ SM 수(38)" 규칙은 1280³에서 −19 %라 기각. 남는 최대 손실은 1536³·256~768×4096²에서 약 7 %(큰 타일이 더 빠른데 작은 타일 선택). `check_args`에 규칙 검사 추가. 최종(`2026-11-10_auto_final.csv`, 클럭 71개 모두 1500 MHz): 이전 최종 대비 모든 모양에서 같거나 빠름. 4096³ 94.4 %, 8192³ 80.1 %, 4095³ 82.9 %, 2048×4096² 92.9 %, 128×4096² 82.3 %. pytest 54 passed / 2 skipped. 벤치 `--tile`은 여러 번 줄 수 있게 바꿨고(`tiles_for`가 모양별 기본 타일 사용), `ncu_collect.sh`에 `SHAPE`/`SUFFIX` 환경 변수와 cuBLAS 8192³ 커널 이름(`Kernel`) 필터를 추가.
- **R17 (2026-11-10): 브랜치 전체 리뷰(`main..g1-sgemm`).** 확인·조치한 것:
  - (측정) k04/k05 `run()`이 호출마다 `cudaGetDevice`·`cudaDeviceGetAttribute`·`cudaFuncSetAttribute`를 불러 CUDA event 시간이 부풀었을 가능성 → ncu `gpu__time_duration`(커널만) 256³ k05 45.89 µs vs event 46.08 µs, 512³ 83.36 vs 84.99 µs. 차이 0.4~2 %로 무시할 수준, 측정 방법 유지. 작은 크기의 낮은 비율은 커널 자체 시간(256³은 128×128 블록 4개).
  - (수정) 커널이 `int`로 인덱싱하는데 인자 검사가 오프셋 범위를 보지 않았다. ld가 큰 부분 행렬이면 `(M−1)·ldc + N ≥ 2³¹`에서 조용히 잘못된 주소를 쓸 수 있었다 → `bad_args`가 A·B·C 각각의 마지막 원소 오프셋이 `INT_MAX`를 넘으면 −1. `check_args`에 C·B 경우 추가.
  - (수정) PyTorch 바인딩이 a·b·c 장치 일치를 검사하지 않고 장치 전환(guard)도 없었다 → 같은 장치 검사(`ValueError`)와 `c10::cuda::CUDAGuard` 추가. GPU 1개라 다중 GPU 동작은 시험하지 못함.
  - (남김, KNOWN_ISSUES #10) grid 차원 한도: K=0 경로 `scale_c`의 grid y = ⌈M/8⌉ ≤ 65535(M ≤ 524,280), k01의 grid y = ⌈N/32⌉, k02·k03 ⌈M/32⌉, k04·k05 ⌈M/BM⌉, 벤치 기준 커널 grid y = M. 넘으면 launch 오류가 반환값으로 올라오고(조용한 오류는 아님) 커널은 실행되지 않는다.
  - (남김) `benchmarks/bench_sgemm.py`의 진행 출력 루프는 커널을 건너뛴 모양에서 일부 줄을 빼먹을 수 있다(CSV는 정상). 표시 문제라 그대로 둠.
  - 확인만: k05 VEC 경로의 16 B `cp.async` 정렬 조건(A·B 16 B 정렬, ld % 4 == 0, 열 오프셋 4의 배수), 3단 파이프라인의 wait/commit 순서, 묶음 열 배치(TN = 4·8·16 모두 0 ≤ 열 < BN), β = 0에서 C 미독출. 검증(672건 × 5모드)과 pytest 63개가 이를 덮는다.
